# 第一步：读取记录、自动补读与 canary 实验

后续进展：2026-11-01 增加默认关闭的生产报告后保留/召回核对，复用本页的读取审计和补读；详见[接入说明](recall-check-2026-11-01.md)。本页下文保留当时的实验机制和结果。

本次改进完成“记录实际返回 → 核对引用函数 → 有限次数补读 → 再核对”的工程闭环，并提供仓库副本上的 canary 实验。由 Python 调度程序收集 OpenCode 的 JSON 事件，不采信模型自行填写的“已读文件”清单。模型声称已读、工具调用成功、源码全文已返回，是不同的事情。

## 接入位置与记录内容

SUBSYS 和 VERDICT 任务启用 `opencode run --format json`。同一事件流包含 OpenCode 原生工具和项目 MCP 工具，不改变生产环境的工具权限。

当前适配以下输出格式：

| 工具 | 如何核对 |
| --- | --- |
| 原生 `read` | 从实际返回的路径、行号和行文本提取证据 |
| 原生 `grep` | 仅记录返回的匹配行 |
| MCP `read_file` | 解析返回行号；默认头 80 行和尾 40 行不能算全文 |
| MCP `search_code` | 仅记录实际搜索结果行 |
| MCP `find_symbol_definition` | 区分完整定义与头 40 行、尾 20 行的截断定义 |
| `bash`、子 agent、其他未适配工具 | 保留调用记录，源码范围为未知 |

每行返回文本必须与运行结束后的仓库源码逐行匹配，才能计入 `returned_ranges`。单行被截断或内容不符时单独记录。源码 SHA-256 用于发现后续变化。外部路径和越出仓库的符号链接不计入仓库证据。

产物默认保存到：

```text
data/read_audit/<任务键>/<批次>/<运行ID>/
  tool_events.jsonl    工具事件原文，不保存独立的模型推理事件
  audit.json          文件摘要、实际返回区间、未观察到的区间、未知调用
  result.json         与本轮证据对应的有效报告草稿
  coverage.json       最终函数范围核对及各轮补读结果
```

可用 `AGENT_READ_AUDIT_DIR` 改变根目录。每次重试使用独立运行 ID，不合并不同尝试的阅读记录。超时保留已收到的事件；写盘失败和恢复旧阶段产物均保持未知。默认目录位于报告临时目录之外，不会在成功交付时被清理。工具原始输出可能包含源码，应按项目数据管理，不提交到 Git。

报告新增“源码引用核对”，将具体 `文件:行号` 或 `文件:起始行-结束行` 与本次记录比较，并另列函数范围与补读结果。

## 自动补读具体怎样运行

1. 从结构化报告和 HTML 正文中提取源码引用，以语法树定位包含引用行的 C/C++/Rust 函数。没有可靠函数边界时只核对被引用的行范围，并明确标注；不会凭空扩成“完整函数”。
2. 将函数起止行与当前有效报告所属会话的实际返回行比较。即使引用行返回了，函数中间缺失仍会发现。
3. 如有可读取的缺口，创建一次独立补读任务，给出路径、函数名、起止行与待核对草稿。要求使用原生 `read` 或 MCP `read_file`，每次最多 200 行，分段读完，再重新生成原任务的全部输出。
4. 独立会话必须重新读取所有固定目标，不拼接上一轮证据。原先目标不会因模型删掉引用而消失；新引用会增加检查目标。补读提示不携带上一轮报告中的 canary 答案。
5. 最多补读两轮。仍缺证据时在最终报告中保留缺失范围，不改变评分，也不宣称“全部读过”；如果补读连有效报告都没有产生，则报错要求重试该阶段，避免交付被写坏的产物。

SUBSYS、VERDICT 默认启用，正常使用原有描述命令即可。只有发现证据缺口才增加模型会话，因此这一步可能增加 API 用量。审计完全不可用、位置无效、文件已变化等情况不会通过盲目重复读取变成通过。JSON 修复及失败重试的证据归属也单独处理，不把后一次失败运行的日志绑定到前一次有效报告。

## 在副本上放置 canary

准备过程不调用模型。先提供人工确认的目标清单，再运行 `prepare`：

```json
[
  {"path":"kernel/mm.c", "symbol":"alloc_page", "confirmed":true,
   "reason":"该函数是内存分配入口，属于本次模块说明必须核对的实现"}
]
```

同文件有多个同名定义时，加 `line` 或 `start_line` 指定函数起始行。工具只接受可完整解析的函数定义，不向宏、汇编或无法可靠解析的函数中猜测插入。

工具创建全新仓库副本，用 `secrets.token_hex(16)` 为每个函数生成 128 位随机值，在函数体左花括号之后插入一条内联块注释：

```c
int alloc_page(void) { /* READ_AUDIT_CANARY:这里是32位随机十六进制值 */
    /* 原来的代码 */
}
```

不新增换行，因此原行号保持不变。修改只发生在副本；原始与修改后文件均记录 SHA-256，插入后重新检查语法树。注释通常不改变函数语义，但这不是对任意构建、宏和源码校验机制的语义等价证明。

答案写入实验目录的 `private/manifest.json`，位于 `repo/` 副本之外；公开目标清单不含随机值，模型提示也不包含答案。它是信息获取实验，不是对拥有任意文件系统访问能力的恶意 agent 的密码学证明。标记放在函数开头，读到标记尤其不能代替完整函数覆盖核对。

实验响应包含 `read_functions` 和 `canary_observations: [{path,symbol,token}]`。评分器分别报告：目标函数数、函数完整返回数、标记实际返回数、标记正确回报数、两者同时成立数，以及错误或未知回报数。仅在提供独立人工相关函数清单 `--gold` 时计算**选择召回率**和漏选函数；否则该指标保持未知。模型自报的 `read_functions` 不作为真实阅读证据。

入口调用候选可以帮助人工准备清单：`inventory` 遍历显式文件里的语法调用，在深度上限内展开可唯一定位的候选。函数指针、外部调用、同名歧义和超过深度的边均单独列出；这些候选默认 `confirmed=false`，不声称是完整调用图或全部相关函数。

## 已完成的验证

2026-10-11 在本机 OpenCode 1.14.48 上启动真实 CLI 和项目 MCP 服务，以本地确定性模型接口发出工具调用。测试没有调用付费模型，因此证明的是工具传输与记录机制，不是模型理解或评价质量。

500 行测试文件依次经过原生 `read` 读取第 81—100 行、MCP `read_file` 默认读取、原生 `grep` 搜索第 300 行，再执行一次无法定位源码的 shell 调用。程序得到：

```text
实际返回：1—100、300、461—500
未观察到：101—299、301—460
无法定位源码范围的调用：1 次
```

真实 MCP `write_report` 成功生成报告。另一项本地确定性联调运行完整 batch 补读流程：首轮缺行，第二轮使用原生与 MCP 分段读满 500 行，再重新核对。

此外，使用用户配置的 **DeepSeek `deepseek-flash`** 完成真实模型验收。合成仓库目标函数位于 `mm.c:3-306`；首轮故意要求只预览，以测试修复触发。实际记录发现缺失行后自动启动补读，最终目标函数完整返回且 canary 正确回报。人工相关清单还包含一个故意未选入目标的辅助函数，选择召回率为 1/2，没有被“目标已读全”覆盖。这是小规模机制验收，不是论文效果或真实比赛仓库的质量结论。

本机验收产物保存在 `/home/niu/agent-read-audit-validation-20261011/`，原仓库、带标记副本、每轮工具日志、报告草稿及评价结果均分开保存；不进入生产仓库。

最终验收在去掉补读提示中的上一轮标记答案后，用一组新的随机值重跑：首轮返回第 1—80、267—306 行，目标函数缺失第 81—266 行；一轮补读后返回第 1—306 行。两轮都能正确回报标记，但只有补读后完整覆盖目标函数，直接说明“标记回报正确”与“函数读全”必须分开。原仓库哈希保持不变。结果摘要为上述目录中的 `verification-summary.json`。

最终相关回归 **212 项通过**，包括真实 OpenCode 与 MCP 的确定性联调、补读成功与耗尽、删引用不能规避、范围引用、旧产物、超时与重试归属、canary 副本与行号、入口候选及人工清单遗漏。新增与修改的审计实现通过 Ruff 检查；报告渲染文件中原有的三个未使用导入告警未在本次清理。

## 实验命令

以下目标清单和人工相关清单都应放在被测仓库外，输出目录必须是新的目录：

```bash
# 可选：生成待人工确认的候选。此命令不调用模型。
python -m oskernel_agent.cli.read_audit inventory \
  --repo /path/to/repo --path kernel/mm.c --entry kernel/mm.c:250 --depth 2

# 创建副本并插入标记，不调用模型。没有人工完整清单可省略 --gold。
python -m oskernel_agent.cli.read_audit prepare \
  --repo /path/to/repo --targets /path/to/targets.json \
  --gold /path/to/gold.json --output /path/to/new-experiment

# 真实模型验证：读取本机 config.toml 的 [api].key/base_url，会消耗 API 用量。
python -m oskernel_agent.cli.read_audit run \
  --experiment /path/to/new-experiment --model deepseek-flash

# 可选：加 --preview-first，故意制造首轮只预览的情况以检验补读；
# --repair-rounds 0 可关闭补读，用于对照。默认最多补读两轮。

# 离线重新核对，不调用模型。
python -m oskernel_agent.cli.read_audit evaluate \
  --experiment /path/to/new-experiment \
  --audit /path/to/run/audit.json --response /path/to/run/result.json
```

`run` 使用独立实验配置，不修改生产工具权限或用户全局 OpenCode 配置。密钥只保存在本机配置中，不要放进目标清单或提交到 Git。默认不开启任何 canary 实验；常规描述报告只启用读取审计与补读。

## 测量边界

工具返回不等于模型注意、理解或评价正确。提示正文、附件、子会话以及后续上下文压缩不在完整测量范围内；未观察到不能直接解释为虚构。源码是在运行后比较的，期间文件发生变化时只能保守处理。`source_read_coverage` 仍为 `unknown`。

本次完成的是第一步工程与实验工具。相关函数清单仍需按任务人工确认；语法候选不能保证查全。标记回报只能作为信息获取的实验信号，不能代替理解或评价正确性的验证。评价准确性、self-consistency 与恶意代码防御属于后续步骤。
