# CFC-Audit 小 demo：工程链路可运行，尚无模型覆盖净收益

2026-09-26。按照所贴方案先做小规模可行性检查，保留[研究方向决策](research-pivot-decision.md)
的停止条件。没有修改旧研究结论，没有清理或重置已有未提交文件。

## 本轮结论

**程序可以发现运行场景没触及的错误处理，并对已经发现的义务实行不可跳过的交付检查。**
但这个 demo 不足以支持“没有静默遗漏”，也没有显示比完整源码加直接测试更好的关键行为覆盖。
账本检查的是响应及引用的存在性，不检查自然语言是否真的解释了所有引用。

最终同模型烟测两组均覆盖既有的 10 个源码要点及“部分失败保留成功前缀”这一额外语义要点
（本轮智能体按旧清单复核，11/11 对 11/11；不是独立专家盲评，也不是自动语义评分）。
候选组提示 token 为对照的 2.62 倍，总 token 为 1.92 倍。
**当前结果只支持保留小型账本机制，不支持扩建完整 CFC-Audit 架构或宣布方法创新。**

## 实现和明确缩减的范围

[demo 脚本](../research/cfc_audit/demo.py)复用 Nginx `ngx_chain_add_copy`、
`ngx_alloc_chain_link` 的已冻结函数正文及源码位置。该功能此前用于开发；此次不冒充新仓库留出实验。
真实 `ngx_palloc` 在夹具中由可控制失败次数的分配替身代替；不编译整个 Nginx。

本机无 Clang 编译器，所以用 GCC 13/gcov 的行计数、分支计数和函数入口计数。
[GCC 13 文档](https://gcc.gnu.org/onlinedocs/gcc-13.2.0/gcc/Invoking-Gcov.html)
说明 JSON 覆盖输出和分支计数；本实验没有间接调用或比较值轨迹。
两次采集在不同的新目录编译运行，避免 `.gcda` 累加污染对照。
覆盖编译与不插桩原始 C 在三个输入上逐项比较，七个输出字段均相同（21/21）。
这不是重新执行旧实验的 180 个输入。

动态计数差异给出种子后，[闭包与账本模块](../src/repo_summary/audit_ledger.py)纳入所在函数全部
源码节点和可用的直接被调函数。整函数覆盖包含未执行条件和错误分支。
按函数和源码顺序每 5 个事件分组；没有实现精确控制依赖聚类、状态读写闭包、别名分析、
SVF、回调注册或整仓库索引。分组可能切开一个条件及其返回，记录中不能把它称为完整语义单元。

程序为未展开的 `ngx_palloc` 和总体分析能力各生成一条 UNKNOWN 义务。
**总体范围声明不能证明每一处未发现代码都已有具体边界。**
未来若实现整仓库索引，还需独立测试解析失败、宏、构建配置、未映射轨迹及状态依赖是否漏记。

## 执行结果

三场景的向量依次为 `old_len, input_len, pool_len, heap_fail_after, feature_enabled`。

| 场景 | 输入 | 返回 | 最终链长 | 分配调用/成功次数 | 剩余空闲节点 |
|---|---|---:|---:|---:|---:|
| 正向 | 1,2,2,-1,1 | 0 | 3 | 0/0 | 0 |
| 对照 | 1,2,2,-1,0 | 0 | 1 | 0/0 | 2 |
| 部分失败 | 1,2,0,1,1 | -1 | 2 | 2/1 | 0 |

正向与对照只改变是否调用该功能。`feature_enabled=0` 是夹具开关，不是 Nginx 内置开关。
失败场景不参与选择动态种子；其覆盖数据在闭包冻结后采集，用来检查新增静态候选。
不插桩版本的三场景输出提前统一生成，仅用于逐项检查插桩是否改变结果。
随后将三场景的输入输出同时提供给两个模型组，直接测试对照没有被扣留失败信息。

- 20 个差异种子节点（包括 2 个函数入口），涉及 2 个函数。
- 26 个源码事件：18 个有正向源码行见证，8 个 STATIC_ONLY。
- STATIC_ONLY 中 2 个是未生成可执行覆盖的声明，不能把 8 个全称为遗漏机制。
- 另外 6 个在失败场景被观察到：失败处 `*ll = NULL`、`return NGX_ERROR`、
  `ngx_palloc` 调用、其空指针检查、`return NULL` 及分配成功的 `return cl`。
- 8 个审计义务；真实模型提交后 DONE 6、UNKNOWN 2、UNPROCESSED 0。

`DYNAMIC_LINE` 只表示源码行级见证，同一行的多个 CFG 节点可能共享一个计数，
不能把它当成精确事件顺序或每个表达式的独立执行证明。

## 账本门禁与真实模型对照

故障注入的 6 项检查全部通过：漏一项禁止报告；重启保留待办；未知不能改成 DONE；
伪造证据 ID 被拒绝；全部交付后允许报告；未知边界出现在报告中。
新增 10 项自动测试及相关旧模块检查合计 **57 passed**；Python 编译检查通过。
环境未安装 Ruff，未声称完成 Ruff 检查。

两个模型组均使用本机已有私有配置的 `deepseek-flash`，每组 2 次调用、每次输出上限 2,200 token。
源码组先写报告再自查；候选组按 5+3 个义务分批解释，最后由程序直接拼接，避免另一个摘要步骤再删掉条目。
报告和原始响应留存；未向研究产物复制凭据。

| 最终运行 | 源码与直接测试 | 闭包与账本 |
|---|---:|---:|
| 既有 10 个源码要点（复核） | 10/10 | 10/10 |
| 部分失败保留已追加节点（复核） | 1/1 | 1/1 |
| 提示 token | 3,063 | 8,033 |
| 输出 token | 1,680 | 1,073 |
| 合计 token | 4,743 | 9,106 |
| 模型调用耗时（秒） | 6.692 | 17.348 |

这是等调用次数、等输出上限的成本测量，**不是严格等总 token 或等时间实验**；
也不是具有自主仓库搜索工具的 Agent 对照。所有源码都已提供，不能从中推断动态发现优于源码搜索。
复核清单沿用 `research/summary_coverage/tasks.py` 中的 10 个 Nginx 源码要点，
额外保留该文件原有的部分失败语义项。没有把其他未知语义要求算成已证明；
11 项只用于描述本次报告内容，不是整个功能完整性的分母。

源码报告中“剩余输入节点被丢弃”措辞有歧义：源码实际是停止追加，不修改或释放剩余输入链。
复核未把这句话认可为“释放输入节点”；不能把 11/11 覆盖解释为没有错误。
候选报告中，某个义务的解释仍可省略属于它的 `return NGX_ERROR`，却完整引用该事件 ID；
同一事实在另一个义务里得到解释。因此当前门禁甚至不证明**逐义务解释完整性**。
它仅保证程序发现的义务有结构化响应，且所有所属事件 ID 都已被列出。

## 开发过程和未通过记录

- `cfc-audit-smoke-v1`：无法映射两个 gcov 函数入口行时立即中止；随后显式映射入口，未删除异常记录。
- `cfc-audit-smoke-v2`：无需模型的完整工程检查通过。
- `cfc-audit-model-v1`：4 次模型调用被接口拒绝，因为 JSON 模式要求提示出现“JSON”一词；
  另有两次短诊断请求定位接口问题，不计入成功运行的质量/成本对照，仍是开发开销。
  账本保持 8 项未处理，没有最终报告。
- `cfc-audit-model-v2`：首次真实解释成功；提示 token 2,259 对 7,414。
  但公共输入未解释函数 ID 的字节偏移及夹具开关，源码组把偏移当位置；
  此轮候选文本未明确写出失败后的已追加前缀保留。全部结果保留，不事后改答案。
- `cfc-audit-model-v3`：给两组共同补齐源码 span、ID 格式、输入字段及开关含义，得到上表最终结果。
  不是多次采样择优，也不能把 v2、v3 当成同一冻结协议的两次重复合并统计。

最终原始目录是 `data/behavior-experiments/cfc-audit-model-v3/`，包含原始 C、覆盖数据、模型请求响应、
账本、报告、源码图及本轮两个实现文件的快照；[紧凑结果](../research/cfc_audit/results.json)
记录关键数据和文件哈希。复现命令见 [README](../research/cfc_audit/README.md)。

## 对下一步的约束

这次验证的是工程可实现性；没有通过研究主线的投入门槛。
保持方案为小 demo，不继续添加 SVF、复杂状态扩张或多智能体系统。
若下一步继续检验研究价值，应按既定决策冻结两个未参与开发仓库、每仓库三个功能的关键行为，
再与源码搜索和直接测试进行同总预算比较。只有遗漏或错误接受率有净下降、有效信息保留量不降，
才有依据扩展系统。账本清零本身不是该比较的成功指标。
