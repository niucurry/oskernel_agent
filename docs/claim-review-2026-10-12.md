# 第二步：关键结论的独立复核与修订

第一步检查“哪些代码实际返回过”。第二步检查“报告中的具体说法是否得到这些代码支持”。它减少错误结论传播，但不会把模型一致或源码引用包装成正确性证明。

## 生产流程

新生成的 SUBSYS 和 VERDICT 先完成原有结构校验、读取审计与补读，再进入结论复核。VERDICT 的硬编码等专门校验保留；本次机制不代替已有校验。

1. 从结构化 `issues`、`highlights`、`summary`、`one_line`、`modules[].summary` 选出最多 6 条结论。优先级考虑已有严重程度、绝对化措辞及引用函数的语法分支数量。分支数量只是复杂程度的代理，不是经过标定的风险分数或完整圈复杂度。
2. 两个新的 OpenCode 会话分别复核同一组结论。第一轮直接核对实现，第二轮优先找反例；两者均看不到对方的答案。复核员需完整读取目标函数，并可继续读取调用者与被调用者。
3. 每条回答包含 `supported / contradicted / insufficient`、简短理由、行号和逐字源码证据。程序独立验证证据位于仓库内、原文一致、目标函数与证据所在函数确实完整返回、源码版本匹配。缺失、重复、伪造或未读证据一律降为 `insufficient`。
4. 两次分别支持和反驳时，才针对存在分歧的条目追加一次复核。第三次必须重新读取源码、核对反例，不自动采用多数票。仍不确定则保留分歧。
5. 有有效证据的反驳、分歧或证据不足时，要求原生成流程修订一次，并同步更新 JSON、HTML、摘要和评分理由。随后对修订版再做两次独立复核，不无限循环。修订后仍有争议的明确标注。

每个阶段初始两次复核；有分歧时额外一次；修订后额外两次。复核会话本身无自动 JSON 修复或重试。原生成流程的单次修订仍使用既有结构重试和第一步有限补读，因此总 API 调用量会超过单纯复核次数。只复核关键结论是为了限制成本，不代表未选结论正确。

## 不会被算成“通过”的情况

- 两份回答来自同一个会话，不算独立一致。
- 模型给出 `supported`，但引文不符或只读到引用行，程序将其改为证据不足。
- 复核工具不可用、会话超时或未写出有效 JSON，结果为证据不足。若完全没有有效复核证据，不触发盲目改写。
- 原报告修订后，旧的复核结果不能沿用；每条结论 ID 绑定字段位置、文本和引用，报告还保存整体 SHA-256。
- 删除结构化条目但在 HTML 保留同一句旧结论，会被标为“仍包含先前未确认原表述”。这个检查只识别原文及 HTML 实体，不声称能识别所有语义等价的改写。
- 恢复历史阶段产物时保持“没有本次复核记录”，不信任模型自填的复核元数据。

## 报告和日志

HTML 在正式结论之前增加“关键结论复核”，列出选中与未选中数量、是否修订、逐条结果、理由与证据。两次支持显示为“两次复核支持”，不会显示为“已证明正确”。争议与证据不足明确提示不能作为确定事实，依赖这些说法的评分需人工核对。子系统的复核状态也传入总评，减少把未确认说法继续当作事实引用。

主问题列表与描述摘要中的未确认条目也携带限定前缀，并标为“待核对的源码说法”。下游一页摘要若引用该条目，必须保留前缀，否则不能通过校验。笼统子系统拆分后的模块摘要也继承相应复核状态。并发子系统的复核任务使用不同运行标识，不共用 OpenCode 临时数据库目录。

默认日志目录：

```text
data/claim_reviews/<批次>/<运行ID>/
  original.json        修订前报告
  selection.json       候选、入选依据及未选条目
  initial/check/       第一次独立复核的输入、原始输出、程序核验结果
  initial/counterexample/  第二次独立复核
  initial/adjudicate/   仅发生分歧时出现
  final/               仅发生修订时出现：新版本的两次复核
  final.json           最终报告
  review.json          汇总及指纹
```

原生工具与 MCP 的原始读取记录仍保存在第一步的 `data/read_audit/`，复核汇总引用对应运行 ID 与文件位置。两个目录均不随临时报告目录删除。可用 `AGENT_CLAIM_REVIEW_DIR` 指定复核日志根目录。源码和报告日志不要提交 Git。

## 使用和复现

升级现有生产配置时，重新运行 `oskernel-setup` 注册 `os-kernel-claim-review`。模型沿用已有配置；使用本次用户提供的接口时执行 `LLM_MODEL=deepseek-flash oskernel-setup`。新复核角色继承项目已有的工具权限，不修改其他角色或全局 OpenCode 配置。之后使用原有描述报告命令即可。

单独验证已有报告的结构化结论：

```bash
python -m oskernel_agent.cli.claim_review \
  --repo /path/to/repo --report /path/to/draft.json \
  --output /path/to/new-validation-dir --model deepseek-flash
```

该命令使用本机 `config.toml` 中的 API 配置，会产生模型用量；启动前检查 MCP 依赖。输出必须位于仓库外的新目录。可加 `--no-revision` 只复核原报告，用于对照。这个独立入口的报告正文内联在 JSON 中；生产管道仍按原来的 HTML/JSON 文件契约运行。

```bash
python -m pytest tests/test_claim_review.py tests/test_setup_opencode.py -q
OSKERNEL_TEST_OPENCODE=1 python -m pytest tests/test_read_audit_opencode.py -q
```

## 验证口径与边界

本机真实模型实验保存在 `/home/niu/agent-claim-review-validation-20261012/`。合成源码包含边界检查和数组累加；故意给模型两条错误描述、一条有源码支持的描述以及一条缺少测量数据的性能断言。小型 C 测试程序在模型之外检查边界返回值与累加结果，标准答案没有放进被测仓库或复核提示。

2026-10-12 最终验收使用 `deepseek-flash`：

| 输入结论 | 两次独立复核结果 |
| --- | --- |
| lookup 未检查负数索引 | 均反驳；原文有负数与上界检查 |
| sum_prefix 直接返回 count，没有累加 | 均反驳；原文循环累加并返回 total |
| 越界索引返回 -1，不访问数组 | 均支持 |
| 所有输入下比标准库快两倍 | 均判证据不足 |

一次修订后，错误问题条目被移除，累加描述被纠正，性能断言不再作为结论保留。修订版的 3 条入选结论均得到两次支持；4 个复核会话 ID 不同，事件流完整，逐字引文与函数读取检查均通过。本轮没有出现支持/反驳分歧，因此未触发第三次复核；该分支由确定性回归测试覆盖。

独立 C 测试使用 `x86_64-linux-gnu-gcc-13` 编译运行：负数及上界索引均返回 -1；有效索引返回 7；数组 `[2,7,11]` 的累加结果为 20，而不是元素数 3。没有进行性能对比测量。模型运行前后源码 SHA-256 一致。

最终相关回归 **272 项通过**，包括复核证据伪造、未完整读取、源码变化、会话重复、分歧追加复核、只修订一次、修订后仍错误、HTML 保留旧说法、工具失败不盲目改写、历史产物不冒充已复核、并发运行目录隔离、描述摘要保留限定、PDF 摘要不允许删掉限定，以及第一步原生工具/MCP 联调。新增复核实现通过 Ruff 检查。此前渲染文件的 3 个未使用导入告警未在本次清理。

成功产物位于 `verified/`，摘要为 `verification-summary.json`，展示预览为 `review-preview.html`。第一次 `live/` 尝试因临时 MCP 依赖已失效而停止，未计为成功；验证依赖现放在持久的 `/home/niu/.cache/oskernel-claim-review-test-deps/`，不改项目依赖清单和模型密钥。

这项验证测试的是“发现已知错误 → 修订 → 新版本复核”的机制，不是比赛仓库上的准确率评估。没有评估新问题召回率、全部 HTML 文字的语义一致性或复杂提示注入攻击。同一模型的错误可能相关，两个会话均支持也可能错；没有运行测试时，不应据此声称性能、运行可用性或完全兼容。
