# 决赛四件套报告改造与验收清单

本文件把《proj18-决赛要求》转成可测试的工程约束。四份报告均由工具自动生成，
不依赖赛后人工润色；任何结论都必须能够回溯到源码、编译/运行日志、Git 提交或查重产物。

## 交付物

1. `summary.pdf`：一页 A4，无超链接，正文采用五号或小四号等效字号。
2. `description.html`：作品描述、问题与模块分析。
3. `development.html`：开发过程、提交异常与阶段划分。
4. `comparison.html`：只围绕最接近的一个历史作品展开对比。

## 共用写作约束

- 先写结论和问题，再写解释和证据。
- 用短句陈述事实，删除“综上所述”“值得注意的是”等空泛连接词。
- 不确定的判断必须显示置信度，不能用肯定语气掩盖证据不足。
- COW、VFS、ELF、IPC、ABI、SMP 等术语首次出现时先给中文解释。
- 摘要只保留影响评审决定的信息；详细源码、日志和提交证据放在 HTML 中。
- 禁止系统占位文案、未完成模型结论、编造路径、编造行号和编造百分比。

## 分报告验收

### 摘要 PDF

- 只有一页；页面尺寸为 A4。
- PDF 中不存在链接注释和 URI action。
- 摘要的总体判断、三份报告结论和问题表述全部由专用摘要智能体生成；程序只负责提供三份结构化输入、校验来源和排版，不使用规则模板代写结论。
- 首屏给出 AI 总体判断，再按作品描述、开发过程、历史作品对比的顺序展开，便于评委沿后三份报告继续核查。
- 最多 5 个问题，每项包括发现事实、评审影响、AI 判断和置信度；问题必须绑定真实来源序号，严重度不得偏离来源，摘要置信度不得高于来源置信度。
- AI 失败、引用不存在的问题、遗漏严重问题、输出套话或无法在 10.5 磅正文字号下完整排入一页时拒绝交付，不允许赛后人工润色兜底。

### 作品描述报告

- 首节为“结论与问题”，覆盖编译/运行、硬编码和严重设计缺陷。
- 硬编码规则扫描只负责定位候选；AI 必须逐条给出确认、疑似或排除结论，并说明方法、
  影响、置信度和真实源码位置。任一候选未经 AI 复核时拒绝生成报告。
- 四类硬编码方法必须覆盖：测试名/ELF 名分支、针对测试的 cache 策略、直接打印结果、
  测试脚本旁路失败。
- 每个模块的评委分析不超过 300 个中文字符；长正文不进入交付 HTML，证据通过源码链接下钻。
- 专有名词首次出现有解释。
- 缺少事实扫描或中文化未完成时拒绝生成，不能依赖赛后人工修改。

### 开发过程报告

- 整份报告由 AI 工具生成；程序只负责提取和复算 Git 客观事实，不用关键词规则替代 AI 阶段结论。
- 问题和总体结论前置。每个程序检出的候选都必须由 AI 明确判为“报告”或“排除”，并给出分析与置信度。
- 报告提交总数、时间跨度和主要贡献者。
- 明确给出“大规模提交”的计算口径，不使用无定义的形容词。
- 阶段由 AI 结合提交主题、时间和文件证据归纳；每段列出 AI 结论、划分依据、置信度、时间、关键提交、LOC 和主要文件。
- 程序验证 AI 引用的 SHA，并要求阶段连续覆盖全部可见历史；虚构证据、空缺、重叠或 AI 失败时拒绝交付。
- 提交次数门槛必须来自当届章程；未知时明确写“未配置，不能判断提交缺失”，不自行认定违规。

### 对比分析报告

- 只选择一个最接近历史作品作为主对比对象。
- 给出总体相似度口径，并按模块相似度从高到低排列。
- 每个模块先给简短结论，再给可折叠的函数、文件和代码证据。
- 公共上游、第三方库、ABI 约束和机械误报不计入相似结论。

## 实施阶段

1. 统一摘要数据契约与可读性门禁。
2. 精简作品描述报告并新增日志、硬编码证据。
3. 新增开发过程分析报告。
4. 将对比报告收敛为单一最近作品。
5. 新增一页摘要 PDF。
6. 扩展前端、批处理、测试与真实样例验收。
