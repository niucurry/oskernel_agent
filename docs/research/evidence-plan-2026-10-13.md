# 评价项先确定必要证据，再核对和补读

本次按[用户确认的计划](evaluation-improvement-plan.md)第 1、2 条，补上“先确定评价项和必要证据”的接口。此前读取审计主要从报告引用反推目标；本次增加一份独立于报告的目标清单，处理模型没有引用某个必要文件时的遗漏。

这一步完成的是清单驱动的证据获取，不是完整评分制度、自动相关性检索或行为验证。现有六维评分继续沿用原流程，不能因这张清单读齐就称为已验证分数。

## 程序具体怎样运行

评测方在被评价仓库之外准备 JSON 文件，通过 `AGENT_EVIDENCE_PLAN` 显式指定。系统不从参赛仓库自动加载评价规则；清单路径或证据符号链接越出允许位置会被拒绝。文件放在仓库外只是输入来源约定，不是对任意本机修改者的安全隔离证明。

每项写明：所属维度、要回答的问题、适用范围、判断规则、预期分数影响，以及必须核对的证据。没有正式比赛细则时，不自动编造分值；示例中的 `score_effect` 因此明确写为暂不评分。当前证据不足策略固定为 `needs_review`，不接受自动通过或自动判失败。

例如，“默认请求重试次数”至少需要入口循环、单次请求结果和默认次数配置：

```json
{
  "version": 1,
  "plan_id": "retry-evidence-v1",
  "items": [{
    "id": "retry-count",
    "dimension": "功能性",
    "question": "默认配置且每次请求失败时，总调用次数由哪些代码决定？",
    "scope": "send_request 的默认配置执行路径",
    "decision_rule": "核对入口循环、单次请求结果和默认次数配置；随后用独立测试核验行为。",
    "score_effect": "本轮只核对证据获取，未建立数值评分映射。",
    "on_insufficient": "needs_review",
    "subsystems": ["网络"],
    "evidence": [
      {"id": "entry", "purpose": "入口循环与退出条件", "path": "request.c", "symbol": "send_request"},
      {"id": "attempt", "purpose": "单次请求的结果", "path": "request.c", "symbol": "request_attempt"},
      {"id": "config", "purpose": "默认重试次数", "path": "config.h", "start_line": 1, "end_line": 1}
    ]
  }]
}
```

这些路径是示例，不能直接当作任意比赛仓库的必要证据。相关性由评测方确认；后续可用检索候选辅助准备，但候选本身不成为真值。

运行流程如下：

1. 在调用模型前读取并复制清单。函数目标经 C/C++/Rust 语法解析定位到完整定义；同名定义需要额外给 `start_line`。配置、声明等使用明确行范围，不凭行号猜测函数。无法可靠解析、函数缺失、同名歧义和行号越界保留为定位缺口，不解释为功能未实现。
2. 保存清单原始字节哈希、解析后的清单及涉及文件的 SHA-256。这里的快照覆盖声明的证据文件，不代表冻结了整个仓库或构建环境。
3. SUBSYS 只接收 `subsystems` 指定的项目；`["*"]` 表示每个子系统，空列表表示只交给总评。VERDICT 核对所有项目。正常同一次描述流程中，两阶段共用同一份已解析清单，期间修改清单文件不会偷偷替换本轮规则。
4. 将清单范围加入现有 `required_source_ranges`。模型仍按原任务输出报告；宿主程序比较真实工具事件。原生 `read` 与 MCP `read_file` 都支持，其他通道沿用已有审计适配规则。清单与报告引用各自提出读取要求，报告删除引用不能取消清单要求。
5. 可读取但缺少返回记录的范围触发已有补读流程，最多两轮；新会话重新读取所有固定目标，不拼接会话。源码在运行中变化时原哈希失效，保留缺口，不用新版本覆盖旧版本的要求。定位失败不会触发无意义重读。
6. 报告增加“评价项的必要证据”，逐项显示目的、真实位置和返回状态。读取齐全时仍写明“行为尚未验证，本步骤未计算分数”。原有独立复核若引发报告修订，固定清单也随修订任务保留，最终表使用修订后报告所属会话的记录。

启用清单的相关 SUBSYS 会绕过旧产物自动复用，重新采集本轮证据。显式恢复旧阶段仍没有新的审计记录；总评会按清单重新核对，旧节点不会被标成已完成清单。未启用清单时保持原有恢复流程。

清单与每轮检查结果保存在读取日志的 `coverage.json` 中，路径沿用 `AGENT_READ_AUDIT_DIR`。报告中的清单状态只由宿主程序写入，不信任模型提供的同名字段。

## 怎样使用

先检查清单是否能定位，不消耗模型用量：

```bash
python -m oskernel_agent.cli.evidence_plan inspect \
  --repo /path/to/competition-repo --plan /path/outside-repo/plan.json
```

正式描述仍使用原入口，在启动前指定：

```bash
export AGENT_EVIDENCE_PLAN=/path/outside-repo/plan.json
# 随后运行原有描述报告命令
```

本次提示直接加到请求中，不要求重新注册角色。清单格式错误会在模型调用前报错；正确格式下的定位缺口会保留并展示。

独立的小范围验证入口：

```bash
python -m oskernel_agent.cli.evidence_plan run \
  --repo /path/to/repo --plan /path/outside-repo/plan.json \
  --output /path/to/new-validation --model deepseek-flash
```

`run` 使用本机 `config.toml` 的 API，消耗模型用量，输出必须是仓库外新目录。生成 `plan.snapshot.json`、`report.json`、`evaluation.json` 和每轮读取日志。实验配置和凭证留在本机私有目录，不要提交 Git。

`--omit-first retry-count/config` 仅用于故障实验：首轮模型看到的局部预览清单暂时不含这条证据，宿主完整清单仍包含它。模型被要求只预览给定文件；后续补读会取消预览限制。模型可能自主读到遗漏文件，因此实验结果必须检查真实轨迹，不能仅凭设置了此参数就宣称成功制造遗漏。`--repair-rounds 0` 关闭补读以便对照；正常默认最多两轮。

真实联调还发现独立实验配置的原生 `read` 权限路径与当前 OpenCode 不匹配。已修正 canary、结论复核和本次实验入口共用的配置生成：原生读取规则包含相对工作树的路径，外部目录规则包含仓库根目录与内部文件。依据当前安装版本 [OpenCode 1.14.48 的 read 实现](https://github.com/anomalyco/opencode/blob/v1.14.48/packages/opencode/src/tool/read.ts#L168)，并以真实工具返回验证。生产角色权限未改动。

## 本轮验证结果

2026-10-13 使用本机配置的 `deepseek-flash` 和真实 OpenCode/MCP，在项目外的两文件合成仓库完成对照。清单包含入口函数、单次请求函数和配置，共三项。

| 运行 | 首轮返回 | 补读 | 最终返回 |
| --- | --- | --- | --- |
| `preview-baseline` | 2/3 项；缺配置 | 关闭 | 2/3，保留缺口 |
| `preview-repair` | 2/3 项；缺配置 | 一轮 | 3/3，均在新会话内返回 |

两组首轮报告均没有 `config.h:行号` 的源码引用，只有“尚未读配置”的说明；读取日志也确实只有 `request.c`。清单独立要求 `config.h:1`，因此能发现原有报告引用检查不会提出的要求。补读会话重新读取 `request.c` 和 `config.h`，前后会话 ID 不同；没有把首轮记录倒算成补读会话的输入。两组所有正式验收会话均成功使用原生 `read` 与 MCP `read_file`，没有工具错误，源码运行前后 SHA-256 一致。

首次 `baseline/` 尝试把“完整读取”和“故意漏读”同时交给模型，模型主动读齐；同时暴露了上述原生读取权限问题。该次记录保留，但不算漏读补救的成功样本。随后改为局部预览输入后才完成表中的对照。

关闭补读组耗时约 13.1 秒，允许补读组约 23.7 秒，只是这两次运行的墙钟时间，不是同预算质量比较。没有测量比赛仓库准确率、真正相关证据召回率、数值评分误差或语义理解提升。

本机原始产物位于 `/home/niu/agent-evidence-plan-validation-20261013/`：

- `plan.json` 与 `repo/`：本轮评测清单和小型被测仓库；
- `preview-baseline/`、`preview-repair/`：每轮报告、工具事件、文件范围和清单状态；
- `verification-summary.json`：程序重新读取轨迹、检查首轮遗漏、补读完整性、会话独立性及源码哈希后的摘要；
- `evidence-preview.html`：两组证据表的对照预览。

最终相关回归 **299 项通过**，包含真实 OpenCode/MCP 的确定性联调。专项回归涵盖未引用配置的补读、预算耗尽、源码变化、同名函数、解析失败、路径越界、清单来源、旧产物与模型自报不可信，以及生产 SUBSYS/VERDICT 绑定同一清单。新增和修改的 Python 核心实现通过 Ruff，`git diff --check` 通过；HTML 渲染文件原有的三个未使用导入未在本次清理。工程测试不代替评价效果实验。
