# 把评价项变成带范围的事实断言

本轮继续[用户确认的计划](evaluation-improvement-plan.md)第 4 条，接在“评价项必要证据清单”之后。清单解决需要读哪些材料；断言明确这些材料将被用来判断哪一句话。

例如，默认重试配置为 3 时，“总共调用 3 次”和“首次调用后额外重试 3 次”是两个不同判断。不能仅因为它们都引用了同一个循环，就把它们视为同一结论。

## 本轮具体改了什么

启用 `AGENT_EVIDENCE_PLAN` 的新 SUBSYS 和 VERDICT 任务，在原报告 JSON 中增加 `evaluation_claims`。每个评价项必须恰好一条，无法确认也要保留这一项并说明原因。系统提示要求先形成这些断言，再据此组织正文；当前尚未将全部自然语言正文改为由程序仅从断言生成，因此不声称正文所有内容都已核验。

一条断言的形状如下。实际输出中，`evidence` 应覆盖清单里的每一项必要证据，不能只引用配置：

```json
{
  "item_id": "retry-count",
  "statement": "总共调用 4 次，其中额外重试 3 次。",
  "scope": "send_request 的默认配置执行路径",
  "conditions": ["使用默认次数配置", "每次请求均失败"],
  "evidence": [
    {"evidence_id": "config", "ref": "config.h:1-1", "quote": "#define DEFAULT_RETRIES 3"}
  ],
  "counterevidence": ["需要检查配置是否被覆盖，以及成功返回时是否提前退出"],
  "missing_evidence": ["entry", "attempt"],
  "limitations": "这里只展示配置引文，尚缺入口和单次请求证据。",
  "assessment": "insufficient",
  "validation_need": "execution"
}
```

`scope` 逐字沿用评测方给定的范围；`conditions` 说明结论成立的具体条件；`counterevidence` 是待查的反例方向，不等于确认发现了问题。`validation_need` 是后续验证动作的候选：具体调用次数、返回值和边界行为填 `execution`，纯静态事实填 `static_review`。这个字段是模型建议，不是已运行证明。

检查分成三层：

1. **结构检查。** 项目 ID 必须来自清单，不能漏项、重复、改变预定 scope 或填写“测试已通过”。证据不足是合法回答，但须说明原因。格式不合格接入已有的一次交付重试；仍不合格时生产阶段报错，不悄悄交付缺项报告。
2. **来源检查。** 每段引文必须与仓库原文逐字相同，并位于它声明的 `evidence_id` 目标中。程序核对本轮实际返回记录和固定文件哈希；引用函数需完整返回，不能只读引用行。清单的每个必要证据都需有有效引文，配置等非源文件也支持。来源检查通过只得到“待语义复核”，不能直接得到“结论正确”。
3. **独立语义复核。** 来源齐全且作者提出确定说法的断言，优先进入现有复核预算。复核会话拿到问题、范围、成立条件、反例方向，以及全部必要读取范围。它必须自己重新读取，包括配置，不能把作者贴出的引文当作已读证据。两个初始会话互不见对方结论；有支持/反驳分歧时按原机制追加复核。

本轮沿用每批最多选 6 条关键说法的默认预算，断言优先于普通报告摘要。数量超过预算的断言显示“未完成独立复核”。作者明确写 `insufficient`，或来源核对有缺口的断言，不会被送去为“我不知道”投支持票，也不会因被跳过而变成通过。

有有效纠错依据时，原流程仍最多修订一次。修订必须保留每个评价项，并同步修改断言和相关正文。断言 ID 绑定清单快照、完整条目及声明内容；文字、条件或引文变化都会生成新 ID。复核结果还绑定整份原始报告哈希，因此旧结果不会自动适用于新版本。修订后的报告重新读取、核对并独立复核。

## 报告怎么看

新增“按评价项核对的事实断言”表，保留问题、结论、范围、成立条件、反例方向、证据位置和核验结果。

| 显示状态 | 具体含义 |
| --- | --- |
| 来源核对通过，待语义复核 | 指定材料和引文可追溯，尚未确认推断是否成立 |
| 两次源码复核支持 | 两次独立会话均认为源码支持限定条件下的断言 |
| 反驳或分歧 | 有相反判断，需要纠正或继续核验 |
| 证据不足 | 缺少可用材料、有效引文，或模型明确无法确认 |
| 未完成独立复核 | 超出本轮复核预算，或结果未绑定当前报告 |

所有条目目前都明确保留 `execution_status=not_run` 与 `score_status=not_computed`。本轮不增加自动执行参赛代码的入口，也不把模型支持改成运行测试通过。原有六维评分尚未改造成由这些已核验断言计算，仍需后续按计划接入。

模型生成的是 `evaluation_claims`；报告展示的 `evaluation_assertions` 由宿主程序重算，旧产物和模型自填的核验状态不能被当成本轮记录。条件是否合理、断言是否真正回答了问题仍需语义判断，字符串相同和引用真实不能代替这个判断。

## 使用和留档

正式描述入口在设置 `AGENT_EVIDENCE_PLAN` 后自动启用，不需要新增配置项。未提供评价清单时，保留原有关键说法复核。

独立实验在上一轮命令上增加 `--claims`：

```bash
python -m oskernel_agent.cli.evidence_plan run \
  --repo /path/to/repo --plan /path/outside-repo/plan.json \
  --output /path/to/new-validation --model deepseek-flash --claims
```

它使用已有 API 配置，生成报告后运行独立复核及必要的有限修订，会增加模型用量。`--claims` 不与首轮局部预览故障选项 `--omit-first` 混用。

实验输出包括 `report.json`、`assertions.json`、`review.json`、`evaluation.json` 和读取日志。复核日志中增加 `assertions.initial.json`、`assertions.final.json`，分别保存来源检查与最终状态。生产日志仍使用 `AGENT_READ_AUDIT_DIR` 和 `AGENT_CLAIM_REVIEW_DIR`，不随报告工作目录清理。

## 本轮实际验证结果

验证材料保存在 `/home/niu/agent-assertions-validation-20261013/`，模型为 `deepseek-flash`。示例仓库只有两个文件：`config.h` 定义 `DEFAULT_RETRIES=3`，`request.c` 中单次请求恒返回失败，重试循环从 0 开始，条件为 `attempt <= DEFAULT_RETRIES`。评价清单要求同时读取入口函数、单次请求函数和配置。

进行了两个真实模型实验：

| 实验 | 实际结果 |
| --- | --- |
| 正常生成 | 模型写出总调用 4 次、额外重试 3 次，三项必要证据齐全，两个独立源码复核会话均支持。 |
| 人工放入错误结论 | 保留实际读取记录和真实源码引文，只把断言改为总调用 3 次、额外重试 2 次。来源检查仍通过；语义复核发现计数错误，一轮修订后变为 4 次、3 次，两次新的独立复核均支持。 |

第二个实验保留了一次实际失败：初始两个模型都反驳了错误计数，但其中一个将引文写成 `request.c:10-18`，实际粘贴的内容包含第 19 行。程序因原文与行范围不匹配，将该次判断降为“证据不足”，没有把它计为有效反驳。因此初始合并状态是 `insufficient`，不是“两次有效反驳”。另一份反驳证据有效，足以按已有规则触发一轮修订；最终两份新复核的引文均通过检查。最终复核过程中还出现了两次错误的工具名称调用，模型随后使用正确的 MCP 工具完成交付，原始日志保留这些失败。

这项实验检验的是“真实引文仍可能搭配错误结论，以及系统能否发现并修订”，不是测量模型自然犯错率，也不是大规模准确率评测。没有修改示例源码，其前后哈希一致。

另外在模型会话之外编译运行了评测用 C 程序，观察到总调用 4 次、额外重试 3 次、返回值 -1。这个程序用于核验本次实验的答案，存放在示例仓库之外；**它尚未接入生产自动验证流程**，所以两份最终断言记录仍为 `execution_status=not_run`，分数仍为 `not_computed`。

相关回归共 **328 项通过**，覆盖断言格式与缺项、引文真实性、配置读取、完整函数读取、源码变化、旧复核失效、预算之外保留待核验、修订重审、生产总评接入和已有报告流程。目标 Python 文件的 Ruff 检查与 `git diff --check` 通过。

## 这一轮的边界与后续

本轮建立“评价项 → 明确断言 → 来源检查 → 独立源码复核”的连接。源码摘要中的范围和条件因此有固定位置，程序也能识别缺项与失效复核。

接下来按原计划，为可执行的客观断言接入评测方控制的独立测试，记录输入、实际输出、源码版本和验证条件。只有完成这一步，才可以为特定条件下的运行行为提供模型之外的支持。canary 的语义抽查、完整预算调度和已核验事实计分仍分别按原计划推进。
