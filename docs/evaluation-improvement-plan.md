下面按“输入是比赛要求、评分细则和完整 repo，输出是分项评分及评价报告”来设计。**这些是待实验验证的方法设计；能够直接保证的系统属性，以及只能通过实验提高的评价准确性，需要分别表述。**

1. **先明确评价对象，把“评价准确”拆成可验证的要求。**

   系统输入至少包括比赛要求、可信评分细则、固定版本的仓库，以及 token、时间和执行资源预算。评分规则由评测方提供，不能让参赛仓库中的 README 或其他文件修改。

   每个评分项应明确四件事：评价什么、需要哪些证据、如何给分、证据不足怎么办。例如：

   | 评分项 | 需要确认的事实 | 证据来源 | 可采用的验证 |
   |---|---|---|---|
   | 功能完整性 | 要求的功能是否实现并可达 | 入口、调用关系、实现代码 | 功能测试、调用路径检查 |
   | 正确性与健壮性 | 给定条件下行为是否符合要求 | 分支、边界处理、异常路径 | 边界测试、反例验证 |
   | 效率 | 关键路径是否满足资源要求 | 算法实现、配置、运行结果 | 基准测试、复杂度分析 |
   | 可复现性 | 能否按规定方式完成运行 | 依赖、启动脚本、配置 | 隔离环境中的复现 |
   | 可维护性 | 是否符合明确的工程标准 | 模块关系、接口、重复实现 | 静态分析、专家评分锚点 |

   “代码好不好”由此变成一组具体判断。题目特定 rubric 已有相关研究，因此这里可以借鉴其方法，把研究重点放在仓库级证据获取和验证上。[Rubric Is All You Need](https://arxiv.org/abs/2503.23989)

   同时，把老师的两个问题进一步区分为：

   - **访问真实性：** agent 声称看过的内容，是否真的进入过模型输入？
   - **证据完整性：** 某个评分项所需的关键证据，是否已经找到？
   - **判断正确性：** 已找到的证据，是否足以支持评价和评分？

   三者分别测量，才能知道方法究竟改善了哪一步。

2. **针对问题1，先建立“确定性仓库清点＋评分项驱动检索＋外部访问记录”。**

   首先用程序建立仓库清单和结构索引，包括文件、函数、类、配置、入口、依赖及可解析的调用关系。为代码单元分配与版本绑定的标识，例如：

   `仓库版本 + 文件路径 + 符号名 + 代码范围 + 内容哈希`

   这一步的作用是明确“仓库里有哪些东西”。解析失败、动态调用和无法识别的文件要显式记录，不能默认为不存在。

   随后，根据评分项建立需要寻找的证据。例如，评价“失败重试机制”时，至少要查找调用入口、重试循环、次数配置、异常分类和退出条件。检索采用多种渠道结合：

   - 关键词和符号检索定位候选；
   - 语义检索补充命名不直接对应的实现；
   - 调用与数据依赖扩展跨文件上下文；
   - 从配置、测试和启动脚本反向查找实际生效的代码。

   **老师提出的“先让大模型选相关函数”，可以放在候选生成阶段。** 但它不应独自决定哪些函数算真值，否则预选模型漏掉的代码，后续就无法被认定为漏检。对于重要评分项，应额外检查调用者、被调用者和配置覆盖关系。

   实际访问记录由运行框架生成，至少记录请求范围、工具实际返回内容、截断情况，以及真正送入模型的内容。区分“只搜索到函数名”“看了部分片段”“完整函数进入输入”“补齐了相关依赖”。

   这里有两个边界：所有读取渠道都经过框架，才能声称访问记录完整；内容进入输入，只能证明被提供，不能证明模型理解了它。

3. **保留 canary，但把它完善为“访问审计＋语义抽查”两种机制。**

   随机值 canary 适合检验“能否返回特定位置的信息”。它不能直接证明函数被理解，也不能自动证明相关代码查全。PoR 原本证明的是文件可恢复性，借鉴其挑战机制时，需要重新定义你们自己的保证。[PoR 原论文](https://www.arijuels.com/wp-content/uploads/2013/09/JK07.pdf)

   建议采用下面的审计流程：

   1. 评测方选取待审计代码单元，生成本轮随机 canary；映射和答案保存在可信评测端。
   2. 在经过语义影响检查的仓库副本中插入标记，或在读取接口返回的代码视图中加入标记。
   3. agent 正常评价，并提交带位置引用的结构化证据。
   4. 框架冻结本轮访问轨迹，再抽取审计位置。
   5. 审计时限制补读；如果允许补读，将其记录为“审计后补充访问”，不能倒算成此前已经看过。
   6. 将回答与真实输入记录交叉检查。

   两种插入方式的结论不同：插入仓库副本，可以研究仓库浏览行为；在工具返回中加标记，只能研究返回内容的接收和使用。论文中应分开报告。

   **还必须设置一个“只搜集 canary、不分析代码”的投机基线。** 如果这种策略也能得到高审计分，就说明 canary 指标测到的是标记提取能力，不能将其解释成阅读质量。

   再增加语义抽查，例如询问特定输入下的返回值、某个分支的进入条件、配置覆盖后的实际参数。答案应由执行结果、受限程序分析或人工核验确定。这类探针更接近理解能力，但依然只是局部行为检验。

   实验中同时比较无标记版本、带标记版本，以及加入等长度普通注释的版本，检查是否因为标记吸引注意而改善表现。**canary 最适合作为审计和诊断工具，其价值需要通过“是否能发现漏读、是否有额外收益”证明。**

4. **针对问题2，把整篇报告拆成“可核验的评价断言”。**

   不要直接让模型读完仓库后输出一篇综合评价。先让它针对各评分项生成结构化断言：

   ```text
   评分项：异常处理
   断言：对指定网络错误，程序最多额外重试三次
   适用范围：默认配置下的请求入口
   支持证据：重试实现、错误类型判断、默认配置
   潜在反证：配置覆盖、其他请求入口、边界条件
   验证状态：待验证 / 有限验证支持 / 被反例否定 / 证据不足
   分数影响：按评分细则映射
   ```

   这比复核整段自然语言更容易发现问题。例如，程序究竟是“总共调用三次”还是“失败后额外重试三次”，就可以单独验证。

   证据核验分两层：框架确定性检查引用是否真实、版本是否匹配、片段是否实际提供过；模型或程序分析再判断片段是否支持断言。**引用真实，不代表引用足以证明结论。**

   验证方法按断言类型选择：运行行为采用独立测试和反例；跨文件判断检查路径和配置；工程规范使用确定性规则；可维护性等较主观维度，采用明确评分锚点和独立评审。

   对“所有入口都安全”“不存在某类问题”之类全称断言，要求明确分析范围。有限测试通过只能说明相应测试条件下未发现反例，不能扩展成整个仓库的正确性证明。

5. **把“三次 self-consistency”改进为“按风险分配的独立复核”。**

   老师提出只对关键代码重复判断，可以进一步改为：**对可能显著影响评分、且证据可靠性不足的断言增加验证预算。**

   关键性应综合评分影响、功能位置、跨文件依赖、证据缺口和复杂度。复杂度只是一个因素：一行配置可能比复杂辅助函数更影响最终结果。

   第一版系统可以采用以下复核规则：

   | 当前情况 | 下一步动作 |
   |---|---|
   | 缺少关键证据 | 继续检索或扩展依赖 |
   | 证据齐全，但判断存在分歧 | 增加独立判断 |
   | 涉及边界条件或具体运行行为 | 生成并执行验证测试 |
   | 多次一致，但属于重要评分项 | 按规则强制外部验证 |
   | 验证成本过高、预算不足 | 标记证据不足，保留待核验项 |

   复核时，先让第二个 agent 独立形成结论，再展示第一轮判断，减少跟随效应；可改变检索入口、分析角度，必要时使用不同模型。不同模型也可能共享偏差，因此不能把它们当作统计上完全独立的评审者。

   额外评判 agent 应承担“寻找反证”的明确任务：提出可复现反例、定位相反证据或指出缺失依赖。它提出的新问题也必须验证，不能因其角色是评判者就自动采纳。

   可以用下面的原则安排候选动作：

   \[
   \text{优先级}(c,a)=
   \frac{\text{断言的评分影响}\times
   \text{动作预计减少的错误风险}}
   {\text{动作成本}}
   \]

   其中，预计收益最初可以用启发式规则估计，再用开发集数据校准。这是调度策略，不应直接声称具有最优性。还需保留随机审计预算，覆盖模型认为“简单且确定”的部分。

   自适应采样和提前停止已有工作，所以创新不能只写成“按难度少采几次”；你们需要突出**结合仓库证据状态，在检索、重复判断和程序验证之间选择动作**。[Early-Stopping Self-Consistency](https://arxiv.org/abs/2401.10480)、[Difficulty-Adaptive Self-Consistency](https://arxiv.org/abs/2408.13457)

6. **对恶意输入，分别处理指令注入和熟悉模式导致的语义误判。**

   对指令注入，核心是让仓库内容无法改变可信评测规则。参赛方提交的代码、README、注释、仓库内 agent 指令文件，以及运行时打印的文本，都作为待分析数据处理。

   评分细则、工具权限、审计日志和最终计分逻辑放在仓库外。结构化输出经过格式和引用检查，再由可信程序计算分数。注入检测器可用于标记可疑文本，但不要直接删除全部注释和文档，因为其中也有评价所需的信息。执行代码时，使用隔离环境，并由评测方控制测试和结果收集。

   这种控制与数据隔离可以借鉴 CaMeL；但限制 agent 的操作权限，并不等于保证它对代码的语义判断正确，报告内容被误导仍需独立评测。[CaMeL](https://arxiv.org/abs/2503.18813)

   对 NDSS 2026 讨论的 Familiar Pattern Attack，重点应放在具体行为核验。该论文表明，熟悉结构可能让模型忽略细微语义差异，显式提醒也未在相应实验中解决问题。[Trust Me, I Know This Function](https://www.ndss-symposium.org/wp-content/uploads/2026-f2066-paper.pdf)

   建议设计三类针对性验证：

   - **边界与路径验证：** 将重要断言转成具体输入、预期输出及分支条件，检查模型解释与真实行为是否一致。
   - **等价变换一致性：** 对可安全变换的代码生成等价版本，检查相同语义判断是否稳定；变化明显时触发复核。仅比较应当保持不变的评分项。
   - **受控语义变异：** 在独立实验副本中修改边界条件、返回值或配置，验证修改确实改变目标行为，再检查评价能否相应变化。

   这些是需要实验验证的防御候选。尤其要避免仅由模型自己判断是否值得调用工具；否则，熟悉模式带来的错误自信仍会阻止验证。

7. **让最终评分由已核验事实生成，并明确处理“不知道”。**

   最终报告从结构化断言生成，每项评分都能追溯到事实、证据及验证状态。汇总 agent 只负责组织表达，不应在最后一步新增没有证据的评价。

   证据不足不能自动视为“实现不存在”，也不能按“没有发现问题”给满分。建议输出已支持的评分结果和待核验范围；若比赛要求必须给出单一最终分数，则按预先规定的规则将重要未决项交给人工复核。

   在允许的评分制度下，可以输出“尚未解决的评分项可能造成的分数范围”。这个范围来自评分规则和未决项，不是统计置信区间。

   系统还应区分扣分对象：确认存在的问题可以扣分；评价器无法完成分析，本身不能成为参赛代码质量差的证据。

8. **把 RSI 收敛为可以验证、可以回滚的策略改进。**

   如果沿用老师提出的自我改进思路，建议第一阶段只改进三个对象：检索优先级、复核动作选择、验证预算分配。

   每次评测后，根据人工确认结果或可信验证结果，将错误归类为漏检、上下文不足、语义误判、评分规则误用、攻击影响。然后生成候选策略，在独立验证集上比较准确率和成本；达到预设条件才替换旧版本。

   不允许系统自行改写评分标准、真值标签或通过条件，也不能把自己的评价直接当作正确反馈。训练、开发、测试仓库应分离，同源仓库及其变体放在同一划分中。

   这样首先得到的是可测量的策略自适应。是否进一步称为 RSI，要取决于实际改进机制和证据，而不是加入一个“反思自己”的提示词。

9. **实验要同时回答“为什么有效”和“是否值得付出成本”。**

   数据集建议包含普通仓库及其配对版本：

   | 数据条件 | 要检验的问题 |
   |---|---|
   | 原始仓库 | 正常评价质量 |
   | 带已确认缺陷的版本 | 能否发现真实问题 |
   | 带注入文本、功能不变的版本 | 评分是否被恶意指令影响 |
   | 带熟悉模式误导的版本 | 是否出现语义误判 |
   | 无关或等价修改的版本 | 评价是否对无关变化过度敏感 |

   金标准至少包含评分项、必要证据、可接受的替代证据、事实判断和评分依据。客观行为优先使用测试或可核验分析；主观维度由至少两位标注者独立评价，再处理分歧。LLM 可以辅助标注，但不应独自充当真值裁判。

   基线应覆盖：单 agent 单次评价、固定三次 self-consistency、普通多 agent 评价、老师提出的 canary 加关键代码复核，以及完整方法。再分别移除 canary、外部访问记录、程序验证、随机审计和反证复核，观察各模块贡献。

   核心指标包括：

   - 访问声明与实际输入记录的一致性；
   - 相对于人工标注证据的召回率；
   - 评价断言准确率、问题发现精确率和召回率；
   - 分项评分误差及必要时的排名一致性；
   - 攻击成功率与无攻击条件下的性能损失；
   - 拒判比例、人工复核需求、token、执行时间和总成本。

   证据召回率的分母来自标注数据；真实部署时未知“全部相关证据”，只能报告已完成的搜索与验证范围，不能冒充真实召回率。拒判系统也必须同时报告覆盖率，防止靠大量不作判断获得虚高准确率。

   一个特别有价值的诊断实验是：**分别使用系统自行检索的上下文和人工整理的充分上下文，再比较普通判断与验证增强判断。** 它能帮助区分错误主要来自检索，还是来自拿到证据后的解释。

   所有主要方法都要比较相同预算下的效果，并绘制准确率随成本变化的曲线。对攻击防御，还要测试了解防御机制的自适应攻击，固定攻击者可修改范围和查询预算；AgentDojo 可作为这种评测设计的参考。[AgentDojo](https://arxiv.org/abs/2406.13352)

10. **论文贡献应集中在相互衔接的机制上，实施则分阶段完成。**

   可以将待验证贡献表述为三个方面：

   - **覆盖审计：** 结合可信访问轨迹、评分项证据需求和挑战抽查，识别虚构访问与关键证据遗漏。
   - **自适应验证：** 根据评分影响和证据状态，在继续检索、独立复核和程序验证之间分配预算。
   - **鲁棒评价：** 在指令注入及熟悉模式误导下，检验上述方法是否能保持评价质量。

   这些能否成为创新点，仍需进一步与邻近工作逐项比较，并由消融实验支持。canary、self-consistency 和评判 agent 都是组成机制，论文需要说明它们怎样共同降低一种明确的错误。

   实施上，先选少量可运行仓库和少数客观评分项，完成“固定评分细则—访问记录—证据断言—独立测试—分项报告”的最小闭环。随后加入 canary 和三次复核，测清它们各自改善的错误类型；再做自适应调度和攻击实验。这样第一阶段就能得到一个可检验结果：**在相同预算下，哪些错误通过补读解决，哪些必须通过程序验证解决，以及 canary 对发现这些错误究竟增加了多少价值。**
