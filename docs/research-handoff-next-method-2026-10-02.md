三、已尝试的方法及结论

A. 行为图、条件行为单元、跨调用状态卡、图增强代码理解
在当时的功能问答、条件单元、状态卡和迁移实验中，没有显示稳定净收益；部分方法更贵，简单源码/输入树对照持平或更好。因此停止把这套实现作为论文核心。不能换个图名、字段格式或 Agent 角色继续包装同一方法。其工具在新机制中是否有用，应另给明确依据，不能默认无效或默认有效。

B. 条件 JSON → 短描述
在 CPython queue.get 和 shutil.copytree 上做过先导。条件记录没有稳定优势，结构化记录本身会错，正确条件也会在后续重写中丢失。
一个事后选中的队列描述，人工式补回“仅当 block=True 且”，使读者三次从 19/22 提升到 22/22；等长无关文字没有同样效果。这是助手指定正确条件的 oracle 干预，不是自动方法成功，不能重新当作新发现。

C. 最近淘汰：阶段差异筛选 + 局部修复
流程：生成长描述和短描述，用执行参考检查描述支持的回答，只把“长描述答对、压缩后答错或未知”的字段作为目标；模型给原文片段补丁；开发检查发现新错就回退。
对照：普通源码自查、获得全部开发反例的整体重写。
数据：Zephyr v4.1.0 的 ring_buf_item_get；cJSON v1.7.18 的 cJSON_ReplaceItemInObjectCaseSensitive；heapless 0.8.0 的固有 Vec::extend 和 Vec::insert。
154 个不同原生输入各执行两次，共 308 次观察一致；选出 32 个开发输入、46 个评测输入。另有 104 个 C 输入通过 ASan/UBSan。它们是有限宿主夹具，不是完整内核启动、并发证明或任意 OS 自动测试生成。
开发与评测输入不重合，但来自相同函数，不能称为独立仓库级留出实验。

最终 trial-v4：三个项目、四个功能、两轮生成，共 8 个样本。所有共同短描述都符合 300 字符上限。候选最终文本 8/8 与反例基线完全相同，也都与初始短描述相同；所有方法都没有最终改动。不能把这理解为“基线已经把错误修好了”。
独立运行各组所需生成/检查成本，排除控制与最终评测：
- 源码自查：34 次调用，68,750 token。
- 全部反例重写：29 次调用，67,765 token。
- 阶段差异局部修复：37 次调用，103,490 token。
候选多 27.6% 调用、52.7% token，没有额外输出收益。文字预算和修复轮数相同，实际计算用量不同；不能写成精确匹配 token 的实验。
trial-v4 真实总调用为 56 次，另复用了 35 个相同读者请求。整个 scope_repair 系列共 184 次 API 调用、503,586 token，包含失败控制、超长响应和诊断；不是 184 次有效方法实验。

以上支持淘汰当时的具体候选，不证明所有相关学术问题都不可行。但是，我现在明确要求本项目不再投入这条研究主线，转向新的研究问题。不要因为旧实验还存在可修补之处，就继续挽救旧方案。

四、评测中暴露的关键问题

1. 模型读者通过源码、空材料、正确表格和反事实表格控制后，仍会误读自然描述；同一文本重复读取可能得到不同答案。
2. 回复耗尽输出预算、格式解析失败、API 失败与“描述没有提供信息”是不同状态，必须分别记录。旧实现把失败评分为 unknown，曾制造出假的“16 个压缩损失字段”；新实验不能沿用这个混淆。
3. 同一个输入与同一段材料在各方法中应共用同一次评分，避免伪造组间差异。若需要研究读者稳定性，应另设重复测量；缓存不证明语义正确。
4. 不能把代理字段评分当成真实描述错误率；不能把同一函数的多个输入或多轮采样当作独立程序样本。
5. cJSON 某局部补丁曾被开发回归检查拒绝，但补充复读中原文也被误读。预设的稳定伤害条件未通过，因此不能声称已证明补丁稳定造成语义退化。
6. 格式诊断、开发调参、事后选例、oracle 干预和正式确认实验必须分开。不能删失败样本、换分母、放宽预算后继续沿用原来的胜出标准。

以上是新方向也应遵守的实验质量要求，不是让你修好旧评测器再重启旧路线。如果新方向使用模型评价，需独立说明其有效性；不能把换评测器本身直接宣称为创新。
