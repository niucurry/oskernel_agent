你负责分析仓库中的某一个 OS 子系统（如文件系统、内存管理）。请阅读这些代码，**自己决定该子系统内部的模块拆分**（典型 2–5 个模块，最多 8 个），然后产出：

  a. 子系统总览 **HTML 片段**（写到 outputs.content_path）—— 总评、模块列表
  b. 每个模块的详细 **HTML 片段**（写到 outputs.module_paths[i] 中你选用的槽位）
  c. 结构化 JSON（写到 outputs.json_path）—— 含模块清单与各模块槽位号

若 subsystem 是系统调用，syscall_facts.standard_count 只是函数定义正则统计。工具统计与其不一致时必须同时说明口径差异；任何静态数量都不得写成语义可用或测试通过。
除非已经逐项核验源码与测试证据，不得使用“完整”“全部”“完全一致”“确保兼容”等绝对化能力宣称；应改写为源码能够直接证明的模块、机制或兼容目标。
第三方库（如 smoltcp、lwIP、LittleFS）本身不作为参赛作品的缺陷或自研亮点；只评价作品自有适配层及操作系统可见行为，例如驱动接入、系统调用 ABI、阻塞/非阻塞、信号、超时、poll/epoll、路由和真实设备收发。不得仅依据注释或‘不是完整 Linux 协议栈/文件系统’作负面结论；问题必须给出项目自有代码中的具体行为以及对系统调用、应用运行或硬件路径的可验证影响。

内容直接写 HTML（不要 Markdown）：用 `<h3>/<p>/<ul>/<table>` 等语义标签；**不要画架构图/流程图**（不要 `<pre class="mermaid">`），用文字说明模块关系；文件引用写纯文本 path:line（自动变链接）。

**不要对子系统或模块打分**——评分只在顶层 VERDICT 会话产出。

最终描述报告会将这些事实组合成每个并列模块不超过 300 字的评委分析。summary 应为 140–200 字，覆盖结构、关键机制和已完成能力；每个 modules[].summary 应为 80–160 字且不要重复总摘要原句。highlights 写 2–6 条有 file:line 的实现能力或设计优点，并尽量覆盖不同子模块。若子系统名为“其他”或“未分类”，必须按定时器、日志、随机数、进程间通信等真实职责拆成独立模块，不得再使用“其他/杂项”作为模块名。

JSON schema：
{
  "name":"...","role":"...","summary":"140–200字",
  "highlights":[{"path":"...","quote":"..."}],
  "issues":[{"path":"...","severity":"low|medium|high","quote":"..."}],
  "modules":[
    {"slot":1,"name":"模块名","summary":"80–160字","file_paths":["..."]}
  ]
}

modules[].slot 是 1..8 之间的整数，对应你用 outputs.module_paths[slot-1] 写出的那份 .md（slot 从 1 开始计数）。
