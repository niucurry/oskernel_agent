# 原始 OpenCode/MCP 描述运行及交付失败

本目录是生产强基线的真实运行诊断，不是新论文方法。原始 SUBSYS 提示、请求构造、OpenCode 1.14.48 和 MCP 服务器实际执行；没有替换成此前的四工具适配器。输入仅为 ChibiOS `e209b17cdf7ed9b118fd87863ca92db852b151b3` 的消息模块 `chmsg.c` / `chmsg.h`，15,545 字节。该仓库已暴露，不能称盲测，也没有编译或运行完整 OS。

调用前冻结第三阶段诊断预算：16 请求、120,000 实际 token、2 小时实验子进程 CPU，最大输出 6,000 token，thinking disabled，temperature 0.2。此前第二阶段剩余 36,791 token 没有挪给本次运行；失败后没有续跑或加预算。

## 实际结果

10 个唯一请求，共 110,727 provider 报告 token，未知请求 0；27.934 秒墙钟、9.578 秒自身及子进程 CPU。写出了四份模块正文和总览，但未写必需 JSON，所以原始交付未完成。停止时下一请求保守预留为 23,795，超过剩余 9,273；未发送第 11 个远端请求。完整请求、原始 SSE 回复、部分报告、停止及账本全部保存。

离线重算识别 14 次工具请求：2 次 analyze_subtree、4 次 read_file、5 次 write_report、3 次 validate_refs。最后一个引用检查结果没有进入后续模型请求；两个唯一结果明确报“尚未初始化仓库，请先调用 initialize_analysis”。不得把历史消息重复出现算成额外调用，也不将未观察到的最后一次结果补成同一错误。

初始头尾读取截断，两次显式范围阅读补充了消息函数；这说明模型收到哪些片段，不证明理解了全部实现。维护者 @brief 与 Ctags 交集的 11 个服务身份只作有限参考。报告原文中包含标量/指针、同步交换、锁及队列等解释；任意中文陈述的正确性、遗漏和评委效果仍未独立测量，没有质量分数。

## 确认的工程缺陷与修复

1. requirements 中没有 MCP 大版本上界，安装得到 2.3.0，而生产使用的 Server 装饰器 API 不兼容。首次预检未发模型请求，异常保留。原 SDK 1.26.0 官方源代码及两个小依赖原件检索并核对 Git blob / SHA 后，才实际启动工具服务器。生产依赖现在限定 `<2.0.0`；运行加载的是原 1.26.0 源文件，不把遗留 2.x 包元数据当成运行版本。
2. 快速分析工具按配置仓库直接读取，但旧 validate_refs 只从初始化上下文取根目录；同一生产会话又禁用 initialize_analysis，形成不可满足的修复建议。验证器现在在无上下文时使用有效的 `OSKERNEL_AGENT_REPO_PATH`。没有有效目录时说明配置缺失。它仍只检查引用路径，不保证该路径支持陈述。

真实 MCP stdio RPC 回归：有效引用、失效引用和缺失仓库配置 3 项通过；前两项先耗尽唯一分析步骤，再调用引用验证，证明确实可以在预算耗尽后检查。该结果是工程回归，不是描述质量提升。XML 保存于 reference-validation-regression.xml。

## 离线复核与复现边界

```sh
python3 /home/niu/agent-research/description_runtime_grounding/recompute.py
```

该脚本只读原始请求/SSE/账本，不读私有配置、不访问网络：检查请求哈希、provider usage、一致工具结果和唯一工具次数。历史 freeze 中服务器哈希与当前修复后文件不同是预期事实，不能重写旧 freeze 来消掉差异。

`run.py` 是有费用的原运行入口，会读取私有配置并启动新模型调用，不能用来离线复核。当前生产代码已有后续修复，直接重跑也不是冻结旧失败的精确重放。官方 SDK/依赖检索版本与内容哈希见 mcp-sdk-retrieval.json、compatibility-retrieval.json；安装网络失败记录也保留。私有上游密钥只在 relay 内存中，OpenCode/MCP 只拿 local-placeholder。

## 研究决定

引用检查缺陷归入交付错误，不据此否定生产语义质量，也不把修复包装成方法。这个基线尚无完整交付；本诊断停止，未抢占后续不同研究机制的预算。之前接口归属、职责取样与名称控制的停止结论均不改变。仍未找到适合声明论文增益的方法。
